# 排障与使用经验

本文基于 2026-10-11 完成的 OPPO A97 5G（PFTM10）、原厂 ColorOS 14 / Android 14 实测。使用的组合是官方 Shizuku 13.6.0、Shizzi 0.4.0-rc.3 和 FlClash 0.8.99，手机没有解锁、Root 或刷机。

本机已通过 SIM 分享、Wi-Fi 中继，以及**官方 Shizuku 无线启动后断开辅助 Wi-Fi，继续用 SIM 分享代理热点**。这些结果不能直接推广到所有 OPPO 手机，也不代表整套服务能在重启后全自动恢复。

## 先按正确顺序恢复

正常启动顺序是：

1. 确认 Shizuku 已运行，且没有“权限受限”提示。
2. 确认 FlClash 的 VPN 已连接。
3. 在 **Shizzi 内点 Start**，查看连接、VPN 和隧道状态，再连接热点测试。

正常停止时，先在 Shizzi 点 Stop，再停止 FlClash。已经能用时，无须为了复现教程而重启手机、清除应用数据或重新配对。

### 如果误开了系统“个人热点”，出现直连

本案曾在 VPN 停止、Shizzi 自动关闭热点后，由用户手动重开系统热点，结果建立了普通直连共享。这不能记成“Shizzi 自动回退直连”。

按下面的顺序恢复，会短暂断开热点客户端：

1. 打开 Shizzi 检查状态；如果旧会话仍显示运行，先点 **Stop**。
2. 关闭仍然开启的普通系统“个人热点”。
3. 恢复 FlClash，确认 VPN 已连接。
4. 回到 Shizzi 点 **Start**。
5. 客户端重新连接热点，用新的网页请求或视频验证。

**系统热点开关不会替你重建 Shizzi 的代理共享链路。**不要在旧会话仍存在时反复点 Start，也不要把直接重开系统热点当作断网后的快捷修复。

## 按症状查找

| 现象 | 先检查什么 | 下一步 |
| --- | --- | --- |
| Shizuku 已运行，但提示权限受限 | ColorOS 的“禁止权限监控”开关方向 | 按下一节检查，再回 Shizuku 查看提示是否消失 |
| Shizzi 提示未授权 | Shizuku 是否运行、是否授权 Shizzi | 恢复服务和授权后重新检查 |
| Shizzi 兼容性检测不通过 | Test network API、Prefer test networks 两项 | 记录型号、系统和检测结果；不要套用本机成功结论 |
| 手机自己能访问，热点客户端不能 | 是否由 Shizzi Start 开启、VPN 是否覆盖转发进程 | 检查分应用代理及客户端测试条件 |
| VPN 停止后热点关闭 | 是否已恢复 FlClash VPN | 用 Shizzi Start 恢复；不要只打开系统热点 |
| USB 模式更改后 Shizuku 停止 | 开发者选项、USB 调试是否仍开启 | 重新启动 Shizuku，再依次恢复 VPN 与 Shizzi |
| 无线启动一直搜索不到服务 | 是否连着 Wi-Fi、是否允许该网络调试、Shizuku 是否被限制后台 | 按无线启动一节检查；通常不需要卸载应用 |
| 熄屏一段时间后失效 | Shizuku 状态、VPN 状态、Shizzi 状态，哪一项先停止 | 检查对应应用的后台和省电设置，再按发生故障的时长复测 |
| 电脑检测不到手机 | 是否正在走 USB 备用方式、手机是否允许当前电脑调试 | 本机无线启动不依赖电脑能否检测到手机 |

## ColorOS：“禁止权限监控”需要打开

这台 A97 的开发者选项写的是 **“禁止权限监控”**，实测需要把它从关闭改为开启，Shizuku 的 ADB 权限受限提示才消失。

[Shizuku 官方手册](https://shizuku.rikka.app/zh-hans/guide/setup/)写的是“关闭权限监控”。两者表达的是同一个动作：

| 手机界面上的名称 | 对应操作 |
| --- | --- |
| 禁止权限监控 | 打开 |
| 权限监控 | 关闭 |

以手机实际文案为准，不要只照搬截图里开关的方向。改完后检查 Shizuku 的权限提示；仅看到“正在运行”或一个进程编号还不够。

## USB 调试要保留，数据线不用一直连接

本机保留了开发者选项和“USB 调试”，默认 USB 配置选择“不用于数据传输”；有些界面称为“仅充电”。这也是[官方随机停止排查建议](https://shizuku.rikka.app/zh-hans/guide/setup/)中的设置。

需要注意：本案从“文件传输 / Android Auto”切到“不用于数据传输”时，Shizuku 停止过。修改 USB 模式后要重新看一次服务状态，必要时重新启动。不要因为这次停止就反复切换模式或重装应用。

**开着 USB 调试，不等于必须插着 USB 线。**本机已分别通过 USB 启动后拔线使用，以及无线启动后断开 Wi-Fi 使用。不要为了“无线使用”顺手把 USB 调试或开发者选项关掉。

## 无线配对通常只做一次，服务启动是另一件事

如果 Shizuku 已经运行，直接继续使用，不必重新配对。

首次使用官方无线启动时：

1. 让 A97 连接一个 Wi-Fi，或另一部手机提供的热点。A97 开启自己的热点，不等于它已经连接了辅助 Wi-Fi。
2. 按 Shizuku 的“通过无线调试启动 → 配对”引导打开系统无线调试。
3. 系统询问网络授权时，允许这个可信网络；保存过 Wi-Fi 密码不等于已经允许它用于无线调试。
4. 在系统中选择“使用配对码配对设备”，在 Shizuku 通知里输入配对码，再返回 Shizuku 点“启动”。

后续通常只需连到已授权网络，打开 Shizuku 点“启动”。配对关系被删除、应用数据被清除或密钥变化时，才可能需要重新配对。电脑曾经获得 USB 调试授权，也不等于手机里的 Shizuku 已完成无线配对。[官方配对说明](https://shizuku.rikka.app/zh-hans/guide/setup/)

服务启动成功后，可以断开辅助 Wi-Fi，使用 A97 自己的 SIM 上网。**原用户已在这台 A97 上确认：Shizuku 没有因此停止，热点客户端仍能访问外网。**其他机型或更新后的系统仍需各自验证。

一直停在搜索页面时，先检查当前 Wi-Fi、网络授权、无线调试、通知和后台权限。Shizuku 13.6 在具备相应设置权限后可以自行打开无线调试，不必每次都手工反复切换。只有确实无法启动时，再按应用提示排查。

## 后台限制：先找到停止的是哪一层

允许 Shizuku、Shizzi 和 FlClash 按需在后台运行。本案为 Shizzi、FlClash 取消了电池优化限制；无线配对时也需要 Shizuku 能在切到系统设置后继续工作。

遇到熄屏后断网，先分别查看：

- Shizuku 是否仍在运行、权限是否正常。
- FlClash 的 VPN 是否仍连接。
- Shizzi 是否仍显示连接与隧道活动。

这三个状态对应不同问题。不要看到热点名称还在，就认为 VPN 和转发也一定正常。本案约 5 分钟拔线熄屏测试通过，只能说明这个时长内可用；不能据此承诺整夜待机、深度休眠或系统更新后的表现。

## 分应用代理容易漏掉 shell UID 2000

本案中，Shizzi 的转发工作由 Shizuku 启动的进程承担，实际使用的是 **shell UID 2000**。UID 可以理解为 Android 用来区分进程权限和网络归属的编号。

如果 FlClash 被设置为“仅代理勾选的应用”，只勾选 Shizzi 的图标，可能仍然漏掉这个转发进程。这会出现“手机自己的浏览器能访问，热点客户端却不行”的情况。

检查 VPN 的分应用设置是否排除了 shell 或相关系统进程。本案成功时，VPN 覆盖了主用户的 UID 范围，包含 UID 2000。排查时可先记下原设置，暂时取消分应用限制并重新连接 VPN，再测试热点；有效后再决定是否继续细分。

“让 VPN 接管哪些应用”和“这些请求按哪条规则直连或代理”是两回事。**取消分应用限制，不要求把 FlClash 的规则模式改为全局代理。**本案一直使用规则模式，国内目标按规则直连可以是正常结果。

## Shizzi 的 Always 不等于系统“始终开启 VPN”

本案选择的是 **Shizzi 内部的 VPN → Always**：要求它通过可用 VPN 建立共享。请在 Shizzi 中修改并确认当前值。

Android 系统 VPN 页面里的“始终开启 VPN”“阻止未使用 VPN 的连接”是另外两项设置，不是这里的操作。本教程没有把它们设为必改项，也不能把开启其中某个开关当成下游已成功走 VPN 的证据。

本案一次停止 FlClash 的测试中，热点随后自动关闭。但这只证明当次会话的停止行为，**不能证明断开瞬间、所有协议和所有异常状态都绝对无泄漏**。手动重开普通系统热点，还可能绕过原来的共享链路。

## 不要固定隧道名称，也不用先改 offload

Shizzi 会创建测试隧道，让热点通过它转发。[项目说明](https://github.com/carlelieser/shizzi)介绍了这一机制。本案隧道名称曾在 `testtun0`、`testtun1` 之间变化。

普通使用只需检查应用状态；需要看诊断信息时，应识别**当前**测试隧道及热点上游，不能把某个固定名称或 network ID 写死。“没看到 testtun0”不等于没有隧道。

本机没有修改硬件共享卸载（offload）设置，`tether_offload_disabled` 保持未设置，仍然完成了验收。因此，**本机复用这套组合不需要先关闭 offload**。不要把其他 Root 热点教程里的 offload、iptables 或额外端口映射步骤一并搬过来；其他设备出现具体问题时再研究对应原因。

## 怎样确认修复真的有效

测试对象应是连接热点的另一台设备，而不是 A97 自己。测试客户端要关闭自身 VPN 和其他联网通道，Wi-Fi 手动代理选“无”。若用 Windows 测试，还要排除电脑上已有的代理、TUN 接管和其他默认网络出口，否则可能把电脑自己的代理效果误认成手机热点的效果。

使用新的 Google 搜索、新的 YouTube 视频等预期走代理的请求，避免缓存。还可在客户端浏览器地址栏打开：

<https://www.cloudflare.com/cdn-cgi/trace>

它是纯文字页面，查看 `ip=` 和 `loc=`，与本次预期节点出口比对。需要时加新的查询参数重新请求，不要求历史出口地址或地区永远相同。规则模式下不同目标可能走不同线路，应结合当前规则判断。

测 SIM 分享时，关闭 A97 的 Wi-Fi、开启移动数据；测 Wi-Fi 中继时，让 A97 连接上游 Wi-Fi，并关闭移动数据，排除自动回退到 SIM 的可能。

一次成功网页或出口查询能帮助判断基本共享是否工作，但不能替代独立的 IPv6、DNS、UDP/QUIC 或断线泄漏测试。本案未完成这些专项验证。

## 常见问题

### 为什么最后没有刷机或 Root？

目标是让其他设备连接手机热点后直接使用代理网络，原厂系统上的这套免 Root 组合已经实现了基本目标。研究时也没有为这台精确型号和固件找到可靠的解锁、完整备份及独立恢复路径，因此没有继续刷机。

这不是“所有 OPPO A 系列都不能 Root”的结论。同系列名称、同款芯片或存在一个固件下载，都不足以证明某台手机能安全解锁和恢复。没有必要为了已经实现的功能，把未经验证的刷机步骤加进教程。

### 无线启动后能断 Wi-Fi，为什么还不能保证仅 SIM 冷启动全自动？

前者是在 Shizuku 已经成功运行后继续使用；后者是在手机重启、服务尚未运行时重新取得启动条件，是不同阶段。

官方 Shizuku 13.6 有满足条件时的开机启动尝试，涉及 Android 版本、设置权限、配对密钥和可信 Wi-Fi 等条件；这不等于仅有 SIM 时也能随时自举。可查阅对应版本的[开机接收器源码](https://github.com/RikkaApps/Shizuku/blob/v13.6.0/manager/src/main/java/moe/shizuku/manager/receiver/BootCompleteReceiver.kt)。

本案没有验证重启后 Shizuku、FlClash 和 Shizzi 全部自动恢复。当前实用做法是：需要重新启动 Shizuku 时临时借助可信 Wi-Fi，成功后再切回 SIM；USB 启动作为备用。不能把“无线启动后断 Wi-Fi 成功”写成“户外仅 SIM 冷启动也已解决”。

### 换 Shizuku 分支、LADB 或 Termux，能省掉这个条件吗？

增加一个 ADB 客户端，并不会自动让系统在没有监听服务时接受连接。部分分支的离线连接或 TCP 保活功能，也以已有可用 ADB 监听为前提。

Shizuku-Next 存在利用平台竞态的实验性无线启动实现，见其[已研究版本源码](https://github.com/rushiranpise/Shizuku-Next/blob/1206714f73db0f52dd345164f88a1e8a532c2892/manager/src/main/java/moe/shizuku/manager/start/ForcedWirelessDebugging.kt)。本案没有在 A97 验证该路径，也没有用它替换已经成功的官方组合。实验功能值得单独评估，但不应在日常排障时直接替换当前可用方案。

### 反馈问题时需要提供什么？

提供准确型号、Android / ColorOS 版本、三个应用版本、上游是 SIM 还是 Wi-Fi、三个应用的当前状态、最后一个成功步骤，以及客户端新请求的结果即可。

不要公开订阅链接、节点认证信息、设备序列号、热点密码或含私人网络标识的原始诊断文件。出口地址只需在自己设备上核对，公开反馈通常可以描述“符合预期”或“不符合预期”。
