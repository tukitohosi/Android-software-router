# 验收：确认热点客户端真正经过手机 VPN

汇总日期：**2026-10-11**。

本案例已通过免 Root 透明代理热点的基本功能验收：SIM 分享、Wi-Fi 中继，以及无线启动 Shizuku 后断开辅助 Wi-Fi，均有成功记录。以下步骤用于复做验收，也说明每项结论的证据来自哪里。

“手机自己能访问外网”“Shizuku 正在运行”和“客户端连上热点”是不同检查点。最终目标是：**另一台设备关闭自身 VPN、移动数据和代理，只连接 A97 热点，仍能发起新的目标网站请求。**FlClash 使用规则模式，国内直连规则仍可能正常直连；本教程不把规则模式解释成所有流量都必须经过代理。

## 1. 实测基线与证据等级

| 项目 | 本次环境 |
| --- | --- |
| 手机 | OPPO A97 5G，PFTM10 / OP526D |
| 系统 | 原厂 ColorOS 14 / Android 14，PFTM10_14.0.0.3000(CN01) |
| 权限 | 引导加载程序锁定、未 Root；没有刷机、解锁或恢复出厂 |
| Shizuku | 13.6.0.r1086.2650830c，ADB / shell UID 2000 |
| Shizzi | 0.4.0-rc.3，VPN 模式 Always |
| FlClash | 0.8.99，规则模式；VPN 覆盖主用户 UID 范围，包含 shell UID 2000 |

这是成功组合的版本记录，不是最新版声明，也不证明其他 OPPO 型号或其他 ColorOS 构建具有相同结果。Shizzi 此版本仍以 RC 命名。

本文区分三种证据：

- **工具观察：**通过设备状态读取，确认 VPN、热点上游、进程或接口计数等状态；只代表采样时刻。
- **用户报告：**由操作独立客户端的用户确认新搜索、新视频、出口或脱线运行结果。远程操作者未直接观察的内容，不改写成工具实测。
- **待验证：**尚未完成相应测试，不能由其他成功项目推导出来。

## 2. 测试前先隔离客户端的其他上网路径

准备 A97 和另一台测试手机或电脑。配置好自己的可用 VPN 服务，不需要向他人提供订阅、节点或热点密码。

在测试客户端上逐项确认：

1. 关闭客户端自身的 VPN、代理和网络加速功能。
2. 关闭移动数据；电脑同时断开有线网络、其他 Wi-Fi 或其他能联网的适配器。
3. 将所连 Wi-Fi 的代理设为“无”，只连接 A97 的热点。测试期间不要让设备自动切换到其他已保存网络。
4. 使用新搜索词、新页面和未播放过的视频。已有页面、下载缓存和已缓冲的视频不能单独证明网络仍可用。
5. 选取在本次 FlClash 规则中明确经过代理的测试请求，并确定预期出口。比较当次节点与客户端结果即可，不要求它与历史 IP 相同；不能用一个不同规则的直连请求作对照。

每次切换测试场景后都重新核对客户端隔离条件。故障测试中“仍能联网”首先要排除客户端自行启用了移动数据或换网。

## 3. 检查共享链路，而非只看 VPN 图标

开始前在 A97 上确认：

1. Shizuku 显示运行于 ADB / shell，且没有权限受限提示。本机曾通过打开 ColorOS 的 **“禁止权限监控”** 解决该提示；不同系统若写的是“权限监控”，开关方向可能相反，应按实际文案判断。
2. Shizzi 已获 Shizuku 授权、通知和后台权限；兼容性页面的 Test network API、Prefer test networks 均通过。
3. FlClash 的 VPN 已启动，手机自身能够完成目标请求。分应用设置必须覆盖实际转发使用的 shell UID 2000；只允许 Shizzi 普通应用不一定够。
4. Shizzi 的 VPN 模式为 **Always**，再从 Shizzi 点 **Start** 开启共享。不要用系统热点开关代替这个入口。

有 ADB 时，可在本地辅助查看：

```text
adb shell pidof shizuku_server
adb shell dumpsys tethering
adb shell dumpsys connectivity
```

状态输出可能包含设备或网络隐私，只提取下面的结论，不公开原始输出。没有电脑时可以先做应用状态和独立客户端测试，但要把证据标为人工观察。

| 检查项 | 预期含义 |
| --- | --- |
| Shizuku 服务存在 | 权限服务已启动；这一项不证明代理共享成功 |
| VPN 传输状态 | SIM 场景为 CELLULAR + VPN；Wi-Fi 场景为 WIFI + VPN |
| 当前热点上游接口集合 | 只有 Shizzi 创建的测试 TUN，而不是普通移动网络或 WLAN 接口 |
| 转发计数 | 客户端发起新请求时相应计数增长，作为辅助证据 |
| 独立客户端结果 | 新请求成功，且用于比较的代理请求出口符合预期 |

本次测试 TUN 曾名为 `testtun0`、`testtun1`。复做时读取实际接口名，不把 `testtun0` 写成固定成功条件；仅看到这个接口存在，也不等于它是热点唯一上游。

## 4. SIM 上游验收

1. A97 关闭 Wi-Fi，开启移动数据，确认 SIM 自身能够联网。
2. 启动 FlClash VPN，随后从 Shizzi 点 Start。
3. 客户端按第 2 节隔离其他路径并连接热点。
4. 发起新的 Google 搜索，打开新的 YouTube 视频，并对一个明确走代理的请求比较出口。
5. 若具备工具条件，确认 CELLULAR + VPN、测试 TUN 为热点唯一上游，并观察计数变化。

**本次结果：**工具观察到移动网络 VPN、测试 TUN 唯一上游及转发统计增长；独立客户端的新搜索、新视频与出口一致性由用户报告。基本 SIM 透明共享通过。

## 5. Wi-Fi 中继验收

1. 先停止 Shizzi 共享，A97 连接一个可联网的 Wi-Fi。
2. **关闭 A97 的移动数据**，排除手机悄悄改用 SIM 的可能。
3. 确认 FlClash VPN 在 Wi-Fi 上可用，再从 Shizzi 点 Start。
4. 确认 A97 的 Wi-Fi 上游仍保持连接，同时客户端能够连接 A97 热点。
5. 客户端继续保持自身移动数据、VPN和代理关闭，重复新搜索、新视频和出口比较。
6. 有工具时，核对 WIFI + VPN 和测试 TUN 唯一上游。

**本次结果：**工具观察到 A97 Wi-Fi 已连接、移动数据关闭、WIFI + VPN 和测试 TUN 上游；用户报告客户端仍可新搜索和播放新视频，出口与此前一致。这证明了这台 A97 的实际 Wi-Fi 中继能力，而不只是规格或能力标志。

完成后按自己的日常使用方式恢复手机网络。不要把本机结果推广为所有 A 系列都支持 Wi-Fi 与热点并发。

## 6. 免电脑无线启动，再断开辅助 Wi-Fi

这一项检验“无线启动后是否能脱离辅助 Wi-Fi 使用 SIM”，**不需要为了测试而重启手机**。

1. A97 连接一个自己信任的 Wi-Fi。首次使用时，按 Shizuku 的配对指引启用系统无线调试；允许该网络调试并勾选始终允许，完成 Shizuku 自身的六位码配对。
2. 确保本次确实通过无线调试启动服务，而不只是查看之前 USB 启动后仍存活的服务。需要复做时，可先停止 Shizzi 共享和 Shizuku 服务，再在没有 USB 连接的情况下从 Shizuku 的“通过无线调试启动”点“启动”。
3. 确认 Shizuku 已运行，再断开 A97 的辅助 Wi-Fi，开启移动数据。保留开发者选项与 USB 调试设置；不在此过程中更改默认 USB 模式。
4. 确认 FlClash VPN 使用移动网络，随后从 Shizzi 点 Start。
5. 客户端只连接 A97 热点，关闭自身移动数据、VPN和代理，发起新的目标请求。

**本次结果：**2026-10-11，用户明确确认“无线调试启动服务后断开 Wi-Fi 没问题”，其余操作遵循指导，热点客户端可以访问外网。因此，这台 A97 的无线启动后脱离辅助 Wi-Fi 使用已经通过用户现场验收。

这次反馈没有额外提供新的出口 IP、持续时长、进程日志或重启记录，本文不补写这些细节。此前的电脑 USB 授权不等于 Shizuku 自身完成无线配对。

[Shizuku 13.6.0 官方发行说明](https://github.com/RikkaApps/Shizuku/releases/tag/v13.6.0)另外支持 Android 13+ 在可信 WLAN 条件下免 Root 开机启动。但这与本节的手动无线启动测试是两件事；其[开机接收器](https://github.com/RikkaApps/Shizuku/blob/v13.6.0/manager/src/main/java/moe/shizuku/manager/receiver/BootCompleteReceiver.kt)有前置条件和有限的服务发现等待时间，不能据此认定本机已完成自动恢复验收。

## 7. VPN 中断测试：不要误开系统热点

这项测试会中断共享，适合在无重要下载或通话时主动执行。

1. 先按 Wi-Fi 中继场景建立可用共享；让 A97 保持可联网的 Wi-Fi，上游物理网络在测试中始终可用。否则“断网”可能只因为手机根本没有任何互联网连接。
2. 客户端保持第 2 节的隔离条件。
3. 记录起始状态，然后停止 FlClash VPN，保持 Shizzi 的 Always 设置。
4. **不要点击系统热点开关，不要手动重开热点。**在停止后数秒、约 10 秒、20 秒、30 秒记录 Shizzi、热点和客户端状态；有工具时同时记录是否还有 VPN、是否仍有热点上游。使用实际采样时间，不把这些时刻当作保证的关闭期限。
5. 客户端尝试新的请求，区分新请求失败与旧内容仍可播放；同时防止客户端自动换网。
6. 结束后先恢复 FlClash VPN，再从 Shizzi 点 Start 恢复共享。

**本次工具观察：**停止 FlClash 后约 2.7 秒已看不到 VPN；约 5.7 秒热点仍以测试 TUN 为唯一上游；约 10.4、20.4、30.4 秒观察到没有热点上游，而普通 Wi-Fi 互联网连接仍可用。结合会话状态，本次自动停止共享生效。

**曾发生的人工干预：**用户随后明确说明，自己在自动关闭后重新打开过系统热点。此后客户端出现直连出口，工具观察到普通 WLAN 上游。该操作绕过了 Shizzi，不能记录成“Shizzi 自动回退直连”，也不能据此承诺系统热点永远受 Shizzi 保护。

这组间隔采样没有覆盖关闭前每一个数据包，不能证明瞬时、绝对无泄漏。Always 的语义及会话退出行为可参照 [Shizzi 会话实现](https://github.com/carlelieser/shizzi/blob/v0.4.0-rc.3/app/src/main/java/dev/shizzi/TetherSession.kt)，实际表现仍需针对当前系统验证。

## 8. 拔线、熄屏 5 分钟测试

1. 先通过 SIM 场景确认共享可用，A97 Wi-Fi 关闭、移动数据开启。
2. 若当前仍连接电脑，拔掉 USB；保持手机熄屏约 5 分钟。记录实际起止时间。
3. 客户端保持其他联网路径关闭。在间隔结束后发起新搜索或刷新测试页面，避免只检查已缓冲内容。
4. 必要时唤醒 A97 查看 Shizuku、FlClash、Shizzi 状态；不要先重启服务再判断之前是否存活。

**本次结果：**电脑观察到 USB 设备断开；用户报告约 300 秒熄屏后仍正常，新的请求可用，出口地区与此前一致。USB 断开期间远程操作者不能读取手机进程状态。

结论仅为短时间脱离电脑和熄屏可用，不等于长时间待机或深度休眠稳定。第 6 节的无线启动测试没有报告具体时长，不能把本节的 300 秒移植到那一次测试。

## 9. 已通过与仍需单独验证的边界

| 项目 | 本次结论 | 若需要更强结论，应补做什么 |
| --- | --- | --- |
| SIM 透明共享 | 基本功能通过 | 更换系统、应用或规则后，重新检查下游路径 |
| Wi-Fi 中继 | 本机通过 | 其他设备、频段和接入点组合需分别测试 |
| 无线启动后断 Wi-Fi | 用户现场报告通过 | 需要具体时长或日志时，另做带时间记录的测试 |
| 熄屏 5 分钟 | 用户报告通过 | 长时静置、深度休眠、不同电量和恢复新连接测试 |
| VPN 丢失后停止共享 | 本次观察到自动关闭 | 逐包、故障瞬间、崩溃和人工操作等不同场景验证 |
| 重启全自动恢复 | **未验证** | 实际重启后，分别确认 Shizuku、FlClash、Shizzi 和下游新请求全部恢复 |
| 仅 SIM、没有辅助 Wi-Fi 的冷启动免电脑恢复 | **未解决／未验证** | 不能以“无线启动后断 Wi-Fi 成功”替代冷启动测试 |
| 完整 IPv6 转发及泄漏行为 | **未完成** | 使用具备 IPv6 的上游和独立客户端，核对实际路径；看到不可达路由不等于完成测试 |
| DNS | **未独立验收** | 使用可观测的 DNS 测试确认解析路径和预期策略；网页打开不能替代 |
| UDP／QUIC | **未独立验收** | 使用可确认实际传输协议的客户端或测量工具；YouTube 能播放也可能是 TCP 回退 |
| 系统升级后稳定性 | **未验证** | 更新后重新做兼容性、上游、下游和恢复测试 |

这些边界不否定本次基本目标已经达成，也不要求每次日常使用都重复完整验收。只有相关配置、系统或使用目标变化时，才需要针对性补测。

## 10. 公开记录时只保存必要结果

可按下面模板记录新的复测，不附原始状态转储：

| 字段 | 建议记录内容 |
| --- | --- |
| 日期与版本 | 测试日期、手机型号、系统构建、三个应用版本 |
| 场景 | SIM／Wi-Fi 中继／无线启动断 Wi-Fi／VPN 停止／熄屏 |
| 客户端隔离 | 移动数据、其他网络、VPN、代理是否确实关闭 |
| 设备端状态 | VPN 传输类型、测试 TUN 是否唯一上游、是否看到统计增长 |
| 客户端新请求 | 成功／失败，使用的新请求类型 |
| 出口核对 | 与本次预期代理出口一致／不一致／未核对，不必公开 IP |
| 时间与干预 | 实际持续时长；是否手动开过系统热点、重连网络或重启服务 |
| 证据来源 | 工具观察／用户报告／尚未验证 |

不要公开热点名称或密码、SSID／BSSID、设备序列号、具体出口 IP、订阅链接、节点信息、私人文件路径或未经脱敏的截图与日志。若记录需要这些信息协助本地排障，将其留在本地，不纳入公开仓库。
