# OPPO A97：可复用的实测案例

记录日期：2026-10-11。结论是**免 Root 透明代理热点的基本功能验收通过，且无线启动后可断开辅助 Wi-Fi 继续使用**。本文件不等于未来任意时刻的设备状态。

## 已验证环境

| 项目 | 实测基线 |
| --- | --- |
| 手机 | OPPO A97 5G，PFTM10 / OP526D |
| 系统 | 原厂 ColorOS 14 / Android 14，构建 PFTM10_14.0.0.3000(CN01)，安全补丁 2026-07-01 |
| 硬件 | MT6833V/PNZA，arm64-v8a |
| 引导 / Root | 锁定，未 Root；没有刷机、解锁或恢复出厂 |
| Shizuku | 13.6.0.r1086.2650830c；`moe.shizuku.privileged.api`；shell UID 2000 |
| Shizzi | 0.4.0-rc.3；`dev.shizzi`；两个所需 API 支持，VPN 设置 Always |
| FlClash | 0.8.99；`com.follow.clash`；用户自行导入订阅，规则模式 |
| 转发 | Shizzi 测试 TUN 成为热点唯一上游；名称曾为 testtun0 / testtun1；FlClash VPN 覆盖主用户 UID 范围，包含 shell UID 2000 |

这是成功组合，不是“上述版本为最新”的声明。Shizzi 当时仍为 RC。

## 关键配置与处理结果

- Shizuku 曾显示 ADB 权限受限；把 ColorOS **“禁止权限监控”由关闭改为开启**，提示消失。
- 授予 Shizzi 的 Shizuku 授权、通知和后台权限。Shizzi、FlClash 允许忽略电池优化。
- 默认 USB 模式从“文件传输 / Android Auto”改为“不用于数据传输”；切换曾停止 Shizuku，随后重新启动。保留 USB 调试和开发者选项。
- 热点名称和密码、用户订阅保持原值。没有更改 `tether_offload_disabled`（未设置）。
- 日常入口是 Shizzi Start；系统热点开关不负责建立 Shizzi 的代理共享链路。

## 证据分级

| 场景 | 已有证据 | 能得出的结论 |
| --- | --- | --- |
| SIM → VPN → 热点 | 工具观察 CELLULAR\|VPN、测试隧道为唯一上游、转发统计增长；独立客户端新搜索、新视频和出口由用户报告 | 基本透明共享成功 |
| Wi-Fi → VPN → 热点 | A97 移动数据关闭；工具观察 WIFI\|VPN 和测试隧道上游；用户报告独立客户端仍能新搜索、播放新视频，出口与此前一致 | 该 A97 的真实 Wi-Fi 中继成功，不只是能力声明 |
| VPN 停止 | 暂停 FlClash 后，约 2.7 秒观察不到 VPN，5.7 秒仍为测试隧道上游，10.4 / 20.4 / 30.4 秒观察无热点上游 | 此次会话自动关热点，不能证明立即、绝对无泄漏 |
| 误重开系统热点 | 用户后来明确说明手动重开过热点；新 trace 为中国直连出口，工具观察普通 WLAN 上游 | 人工操作绕过 Shizzi；不能记成“Shizzi 自动回退直连” |
| USB 启动后拔线、熄屏 | 电脑观察设备断开；用户报告约 5 分钟后仍正常，出口仍为日本 | 短时脱离电脑与熄屏可用；不是长时待机认证 |
| **无线启动后断开 Wi-Fi** | **用户最新明确报告成功，其他操作遵循指导，热点客户端仍能访问外网** | **已在此 A97 验证免电脑无线启动后可以脱离辅助 Wi-Fi；不再列为未验证** |

早期两种上游出口 IP 与 FlClash 显示一致、地区为 JP。可分享 skill 不保留具体出口地址，今后验收比较当次实际节点，不能要求旧 IP 恒定。

最新用户原话（2026-10-11）：

> 我试过了，无线调试启动服务后断开WiFi没问题，其余流程均与你的指示无异，连接热点可以访问外网，即我们大获成功了。

这是用户现场验收。该次没有额外提供新的出口 IP、持续时长、进程日志或重启记录；不要补写这些细节。“其余流程无异”不等于证明开机自动恢复。

## 未覆盖的边界

- 手机重启后 Shizuku、FlClash、Shizzi 全部自动恢复，未验证。
- 仅 SIM、没有任何辅助 Wi-Fi 的冷启动免电脑恢复，官方路线未解决。
- 长时间待机、深度休眠、系统更新后的稳定性，未验证。
- 独立的 IPv6、DNS、UDP/QUIC 及所有异常状态泄漏验证，未完成。
- VPN 断开到热点关闭期间的逐包行为，未证明；手动重开系统热点可绕过原保护。

这些项目不否定本次基本功能目标已经达成，也不要求每次日常使用重新完整验收；仅在用户目标扩大或发生相关变化时补测。

## 历史路线与文件优先级

最初计划 B 考虑 Root 与自动恢复，但精确设备没有可靠解锁方法、完整备份与独立救砖路径。因此没有实施刷机，用户改用计划 A，并最终完成上述无线启动验收。匹配 OTA 元数据不等于能解锁或救砖。

原始证据在工作区 `outputs/`：

- `OPPO-A97-PlanB-preflight-2026-10-10.json`：早期只读检查。
- `OPPO-A97-PlanA-setup-checkpoint.json`：安装阶段快照，其中“尚未验证”条目后来已推进。
- `OPPO-A97-PlanA-live-validation.json`、`OPPO-A97-PlanA-vpn-loss-test.json`、`OPPO-A97-PlanA-unplug-baseline.json`：后续基本验收和采样。
- `OPPO-A97-方案A使用说明.txt`：无线配置之前的说明，重启后的 USB 路径现在作为备用，不能据此说必须接电脑。
- 本文件补入用户最新无线启动结果；它优先于早期“无线启动断 Wi-Fi 尚未实测”的讨论。

本 skill 不依赖旧工作区仍然存在，不打包这些原始状态文件中的私人网络信息。打包的两个 USB 备用脚本来自已使用的原脚本，保留型号检查和动态安装路径解析。
